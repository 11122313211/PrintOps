# PrintOps 持续目标

## 北极星目标

让不懂印刷的用户在 10 分钟内，把模糊需求转化为完整、可靠、可询价、可交付的印刷订单。每一步都要可解释、可确认、可追溯。

产品成熟度不以“聊天更像人”为主要标准，而以以下闭环衡量：

```text
需求理解 -> 参数补全 -> 工艺推荐 -> 文件预检 -> 报价准备 -> 人工确认 -> 平台交接
```

模型负责理解和解释，规则负责约束，工具负责执行，人负责确认高风险结果。

## 当前阶段：v0.9.1

- 评测集扩展为 111 例脱敏用例（合成语料），按基础/否定/修改/歧义/多产品/尺寸格式/数量表达分组报告字段准确率；完成率口径为"可完成用例"（补全轮次后基座完整）。真实订单语料仍需逐步替换合成用例。
- 尺寸识别支持个位数维度与内/外尺寸语义；包装盒三维尺寸未标注内/外时给出提示。
- 感知修复：否定窗口不跨标点、后续修改轮沿用当前品类、"包装盒"的"包"不再误判为数量单位、多产品数量归属改为"就近跟随其后产品"规则。
- 低置信度字段必须确认，模型推断不能静默写入最终交接单（v0.9.0 已落地）。

### v0.9.1 之前：v0.9.0 多模块与置信度分级

- 规则感知按证据强度分级置信度；生产字段低置信度阻断生成，偏好字段仅提示。
- `estimate_price` 消费带版本的示例价格参数表；工艺推荐区分合版/专版；起印量与开数参考进入校验与交接。
- 代码拆分为 `order_model.py` / `nlu.py` / `tools.py`，会话状态带 `schemaVersion`。
- LLM 规划发送压缩订单摘要；前端基础字段 inline 编辑、进度改为字段信息度、左栏降噪。

### v0.8.2 会话与多产品基座

- 多产品订单保存为带稳定 `itemId` 的独立 `items`。
- 每个产品项都有独立的基础字段、品类参数、信息度和缺失项。
- 通过“处理第 N 项”或 API 的 `itemIndex` 更新指定产品项，避免参数串项。
- 每个产品项可以独立校验、推荐工艺、选择方案、估价和准备待确认询价。
- 所有产品项分别完成并选择方案后，才能生成整体交接摘要；修改产品项会自动使旧方案和整体草稿失效。
- API 路由分发已抽为无网络副作用的契约边界，接口测试覆盖会话、`itemIndex`、错误路由和整体生成阻断。
- 询价请求持久化到会话，使用订单、平台和 `itemId` 生成稳定幂等键；重复请求复用原请求，不重复生成。
- 新增询价状态查询和取消 API；订单字段、文件或平台变化会将待确认询价标记为 `stale`，重启后仍可恢复。
- 订单未完成或未选择工艺方案时，Agent 会阻止询价并明确下一步；人工确认交接单后，待确认询价转为 `confirmed`，仍不会自动提交供应商。
- 右侧订单区显示询价状态、请求编号、刷新和取消操作；新增询价生命周期与 API 契约回归测试。
- 品类参数、尺寸语义、风险边界和供应商能力档案带有知识版本与来源元数据；`/api/products` 和订单响应可追溯当前依据。
- 尺寸语义已在订单模型、迁移逻辑、多产品编辑和导出中统一；模型或旧客户端写入的尺寸别名会被归一化。

这仍不是完整的多产品下单：当前请求闭环只在本地运行，供应商真实提交、报价回写和浏览器端多文件批量校验仍待完成。

## 系统优化路线图（2026-09 前端统一走查发现）

以下为本轮 UI 统一走查时确认的后端议题，按优先级排队；在前端改造完成后逐项消化。

### P0 安全
- 本地 API 无鉴权与限流：任何本机进程/浏览器页面都能调用全部接口。最小做法：启动时生成本地 token 写入内存并由静态页注入，非白名单来源返回 403。
- `/api/settings` 保存的 API Key 以明文 JSON 落盘（`data/llm_config.json`，仅 600 权限）：改用系统凭据库（Windows 凭据管理器 / keyring），或至少提示用户风险。
- 静态服务直接暴露根目录：`/.git`、`data/agent.sqlite3`、`docs/` 等可被直接下载。需要静态路由白名单（仅 /、/index.html、/app.js、/styles.css、/api/*）。
- LLM URL 由用户任意填写，服务端代为发请求，存在 localhost/内网 SSRF 面：校验目标非环回/内网地址段，或仅允许 https。

### P1 可靠性
- `server.py` 全局 `LLM_LOCK` 串行化所有模型调用且 `PLANNER.last_error` 为共享状态，多会话互相覆盖错误信息：按会话隔离 planner 状态，锁粒度降到配置读写。
- LLM 调用为同步阻塞（最长 20s），聊天期间 UI 无流式反馈：改流式响应或至少缩短超时并异步化。
- 重试策略形同虚设：仅 2 次尝试、80ms 退避，且 5xx 与网络错误重试后无抖动；按错误类别设置指数退避。
- SQLite 无 WAL/`busy_timeout`：并发写会触发 database locked；开启 WAL 并设置超时。
- 会话与运行记录无限增长：SQLite 每会话全量 JSON 重写且从不清理，需要 LRU 淘汰或 TTL。

### P2 工程化
- `agent.py` 仍有约 1583 行（拆分后），`_update_order`/`_update_item` 双份近似逻辑与常量重复，继续下沉到 `order_model.py`。
- 关键词 NLU 与 LLM 双轨行为差异需要在评测集固化（同一句话两种模式结果一致性断言）。
- `/api/chat` 文本无长度上限（仅整体 1MB body 限制），应加单条消息长度校验。
- 无打包/发布产物：依赖零安装是特色，但缺少 `pipx`/zipapp 交付与版本清单。

## v1.0.0 受控供应商接入

- 供应商统一实现能力档案和字段适配器，核心 Agent 不写死平台名称。
- 先支持报价草稿、交期查询和字段导出，再考虑真实提交。
- 外部请求默认需要人工确认，具备幂等键、超时、重试、取消和审计记录。
- API Key 只存在本机或受控服务端配置，不进入日志、导出文件和 Git。

## 后续质量门槛

每次发布至少通过：

- Python 单元测试和 API 契约测试
- 脱敏订单评测，关键字段准确率目标不低于 95%
- 多产品隔离测试，确认不同 `itemId` 之间没有字段污染
- 模型不可用时的规则回退测试
- 浏览器端加载、等待、错误重试、刷新恢复和窄屏检查
- `git diff --check`、AST 检查和敏感信息扫描

暂不优先追求完全自主下单、无限工具循环或同时接入大量平台。先把每一项订单做准确、可解释、可交接，再扩大自动化范围。
