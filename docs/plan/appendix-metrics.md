# 附录 D：北极星度量与验收口径

更新：2026-10-15。本文替代原 v0.12 历史度量方案的完成口径和命令说明；旧排期不再适用。**当前可直接使用评测脚本 JSON 和人工走查表；本地事件及聚合器在本文中仍是设计，不代表已实现。** 不存在可依赖的 `evaluate_agent.py --record` 或 `tools/metrics_report.py` 命令。

权威任务卡、参与者分配、评分和原始记录格式见 [USER_WALKTHROUGH](../USER_WALKTHROUGH.md)。下一阶段工作包见 [NEXT_STAGE_PRODUCT_DESIGN_PLAN](../NEXT_STAGE_PRODUCT_DESIGN_PLAN.md)。

## 1. 北极星的唯一完成定义

首次非专业用户从提交第一条有效需求，到当前版本通过必要校验、关键生产参数核对、明确本地确认，并**实际打开与该版本一致的导出文件**。任务内澄清、等待、编辑和导出耗时全部计入。服务启动准备单独记录。

`missingFields` 清空、可生成、用户点击导出、服务器生成文件分别是中间事件，均不能直接作为最终完成。浏览器无法可靠证明用户已保存、打开或理解文件，因此实际拿到产物及内容合格由走查记录确认。修改使确认失效后不得沿用旧版本的完成状态。

初轮为 8 人、每人一个主任务：名片 3 人、单页 3 人、标准宣传册 2 人。至少 7 个任务在 600 秒内独立合格完成。失败、超时、放弃和需要操作帮助的任务均保留在已开始任务分母；补充场景单独报告。关键尺寸/数量错误、串项和过期确认沿用均为 0，全部参与者理解金额不是供应商报价且尚未发送。结果尚待执行；小样本不外推为总体成功率。

## 2. 指标表与证据源

| 指标 | 计算口径 | 当前证据来源 |
| --- | --- | --- |
| N1：10 分钟合格交接完成率 | ≤600 秒、独立完成且独立内容复核通过的主任务数 / 所有已开始主任务数 | 真人原始记录和实际导出；不能用合成评测替代 |
| N2：任务耗时 | 起点至实际产物核对的墙钟秒数；逐人报告，失败/超时保留 | 同一轮走查记录；仅对完成任务给中位数时必须注明分母 |
| Q1：关键错误 | 数量、尺寸、串项、过期确认逐类计数；任何一个使质量护栏失败 | 独立内容评分表与版本证据 |
| Q2：理解 | 金额/发送/文件/修改四题逐题通过人数及原话依据 | 走查理解题；不以点击“确认”替代 |
| D1：澄清与修正 | 达成当前合格版本前的澄清轮数、用户修正次数、操作帮助次数 | 走查记录；辅助诊断，不以减少轮数牺牲确认质量 |
| E1：合成质量 | 字段准确率 ≥90%、可完成用例完整率 ≥80% | `tests/evaluate_agent.py --json` 输出，保持脚本定义 |
| E2：真实质量 | 至少 20 例真实脱敏订单、字段准确率 ≥95%；缺失/空/无效/不足均阻断 | `--release-gate --json` 的真实 verdict、发布判定和进程退出码 |
| R1：恢复行为 | 409、服务中断、鉴权失效、模型回退逐场景结果；未知提交不重复写入 | 定向 API/浏览器与补充任务记录 |
| P1：交互延迟 | 从用户提交到可见反馈、到可操作结果分别测量；注明规则/模型与环境 | 实际环境记录；不把同步 API 响应称为模型“首字” |

真实库为空时 E2 为 pending/发布阻断，不报 0% 准确率。走查没执行时 N1/Q1/Q2 为“未执行”，不根据空日志推导通过。人工任务、示例成本和测试 fixtures 不计入真实语料。

历史“首字 <1s / 规则 <50ms / 重绘面板 ≤3 / TTI <2s / 套件 <30s”曾是设计预算，未经当前环境基线与测试断言确认，不作为本轮已生效的额外硬门槛。正式发布以 [RELEASE_CHECKLIST](../RELEASE_CHECKLIST.md) 为准。

## 3. 当前可运行的取证方式

```bash
# 开发结果：合成与真实分别报告；真实不足时可能成功退出，不代表可发布
PYTHONPATH=. python3 tests/evaluate_agent.py --json

# 发布结果：真实库当前为空，预期退出码 1；不能吞掉失败状态
PYTHONPATH=. python3 tests/evaluate_agent.py --release-gate --json
```

保存完整 stdout、退出码、代码版本及运行环境到受控本地验收目录。敏感内容脱敏后再决定是否入库。现有字段和阈值由评测脚本计算，不在报表里另写一套公式。浏览器证据来自真实测试运行；真人指标来自 [走查表](../USER_WALKTHROUGH.md)，初轮无需先建设分析后台。

## 4. 最小本地事件设计（待实现）

目的：帮助定位停顿和恢复问题，不能代替真人内容复核。建议每条含 `metricsSchema`、随机 `eventId`、随机 `taskId`、`orderRevision`、单调时间或时间戳、品类枚举及结果代码；同一任务与版本需能去重。随机指标标识与真实订单标识的映射仅在必要的本地受控记录中保存，不能简单截短订单号冒充匿名化。

| 事件 | 触发 | 可以证明什么 |
| --- | --- | --- |
| `task_started` | 第一次有效需求提交，任务只开始一次 | 漏斗起点；刷新或重试不重复计数 |
| `review_ready` | 后端认为当前版本满足进入复核的条件 | 可复核，不代表正确或已确认 |
| `confirmation_recorded` | 后端成功保存明确确认，携带对应版本 | 本地确认已记录，不代表供应商接收 |
| `confirmation_invalidated` | 相关变更使旧确认失效 | 旧确认不能计入当前版本完成 |
| `export_requested` | 用户请求导出指定版本 | 仅证明请求发生 |
| `artifact_generated` | 已生成指定版本的导出字节或产物 | 不证明用户已保存/打开 |
| `task_abandoned` | 用户显式终止或走查确认放弃 | 明确放弃；关闭页面/缺尾事件应标未知，不随意猜测 |
| `operation_failed` | 操作失败 | 结果类别、是否可重试、提交结果是否未知 |

需要时可增加 `llm_fallback`、冲突与恢复等诊断事件。内容复核、实际打开文件及理解题仍由观察者记录；不设计一个“export 即成功”的事件。

### 采集与失败边界

- 日志仅含必要随机标识、版本、品类、时间和代码；不记录客户原话、联系方式、文件内容或密钥，不自动外发。
- 指标与业务审计分开。指标写入失败不阻断整理订单，但须能报告指标数据不完整；必要业务审计仍遵守存储契约，不能套用“静默吞掉”。
- 文件可采用本地 JSONL，但具体目录、配额与保留策略在实现时决定；关键开始、确认失效和结束事件不可独立采样，否则会破坏分母与漏斗。容量不足时明确标为数据缺失，不能只保留成功事件。
- 重试以事件/操作标识去重；状态按版本关联。刷新不能创造新主任务，重生成同一产物不能新增一个完成。
- 指标文件默认不混入面向供应商的交接单或完整业务备份；需要研究导出时明确选择范围。

## 5. 实施与验收顺序

1. **先使用人工记录**：冻结任务、环境与评分，执行原始走查；输出逐人耗时、失败原因、理解题和内容复核。
2. **需要自动诊断时接事件**：沿用后端真实版本及结果；验证重复事件、乱序、刷新、确认失效、写失败、磁盘配额、没有终点等情况。事件缺失时报告未知，不产生虚假的完成率。
3. **再实现聚合**：对固定的合成事件流验证分母、耗时、去重与版本失效。空数据输出“无事件”；缺失链路注明证据不足。只有脚本真正存在并验收后才在 README 增加其命令。
4. **按环境保留趋势**：同任务版本、模式和设备的结果才直接比较；样本或口径改变必须显式说明，不拼接成平滑趋势。

不自动新增按周任务、远端遥测、仪表盘或历史文档中的任意性能发布门槛。真实语料门槛和用户是否完成订单各有独立证据。
