# PrintOps 下一阶段产品与设计开发计划

评审日期：2026-10-15。本文保留规划时的目标与基线；后续已按此开展开发，当前实现和测试见 [NEXT_STAGE_ACCEPTANCE](NEXT_STAGE_ACCEPTANCE.md)。计划条目本身不代表用户验证已通过或稳定版已发布。

评审依据：当前工作区的 README、ROADMAP、发布清单、实施验收矩阵、前后端源码，以及上一轮 Chromium 验收截图与报告。本次未重新操作浏览器中的 `file://` 页面，也未重新运行产品测试。以下界面问题属于源码与截图审查发现；用户是否理解、是否更快，需要后续走查验证。

## 1. 下一阶段要交付的结果

**让首次使用的非印刷专业用户，在 10 分钟内独立完成一份规格正确、关键参数已核对、依据可追溯、可供供应商复核的交接单。**

这一阶段围绕“完成一单”组织体验：用户始终知道正在处理什么、还缺什么、为什么要填、结果有何限制、下一步做什么。

已有基础可以继续使用：订单与字段证据、mm 归一、多产品隔离、默认 SQLite 与可替换存储、版本化成本表、供应商中立接口、人工确认和浏览器历史。开发重点是把这些能力组织成清楚、可恢复、可交付的产品流程。

### 北极星的验收口径

| 项目 | 建议定义 |
| --- | --- |
| 首批范围 | 名片、单页、标准宣传册三类已具备基础整理和示例计价能力的任务。先记录各品类结果，复杂包装、多产品任务单独验收。 |
| 开始 | 本地服务可用，用户提交首条有效需求。启动安装另行测量；任务内澄清、等待、修改和导出耗时计入。 |
| 完成 | 当前订单版本通过必要校验，关键生产参数完成核对，用户明确确认，导出内容与该版本一致；走查中实际打开导出文件检查。 |
| 合格 | 数量及单位、尺寸及语义、材料、颜色/面数、后道与产品归属正确；适用品类的页数、装订等必填项无遗漏。待供应商核实的问题独立列出。 |
| 文件条件 | 文件已提供时记录文件归属、基础检查结果及检查范围；未提供时明确“文件待交付”，不能声称文件已检查或可直接生产。测试脚本分别覆盖有文件和待补文件场景。 |
| 主指标 | 10 分钟合格交接完成率 = 在 10 分钟内完成且通过独立内容复核的任务数 / 所有已开始的指定任务数。失败、放弃和超时不得从分母删除。 |
| 初轮目标 | 8 名未参与开发的非印刷专业用户，每人一个指定主任务，名片 3 人、单页 3 人、标准宣传册 2 人，共 8 个主任务；至少 7 个在 10 分钟内独立完成。补充任务单独报告，不混入主指标。属于形成性目标，不是总体成功率证明。 |
| 质量护栏 | 验收任务中关键尺寸错误、数量错误、产品串项、过期确认被沿用为当前确认均为 0；8 人均能区分“示例估算”和“供应商报价”、知道订单尚未发送。 |

“字段已填写”“可以生成草稿”“用户确认”“文件已检查”“供应商已接收”必须分别表达。浏览器触发下载或打印不能证明用户保存成功；产品事件只记录导出请求/文件生成，实际拿到文件由走查确认。

走查前固定任务卡、追问时可提供的业务信息、可接受的规格集合与判定规则。用途相同可以有多种合理方案，不能用单一预设工艺判定所有用户对错。由未参与本次操作的复核者按同一评分表检查输出；主持人不提示按钮位置或操作步骤，发生帮助则记录为未独立完成。逐品类人数较少，结果只用于发现问题，不用于声称每个品类均达到稳定成功率。

真实脱敏订单仍为 0。正式发布仍要求至少 20 例真实语料、字段准确率至少 95%，并完成现有发布清单的其他门槛。合成数据、演示数据和上述小样本可用性走查都不能替代真实语料。

## 3. 建议的工作台结构

桌面保留熟悉的导航、主区域和摘要，但让主区域随任务切换内容。

```text
顶部：订单名称 · 保存状态 · 当前阶段              帮助 / 设置
左侧：当前订单 / 历史 / 示例

主区域：补充需求 | 比较方案 | 核对与交接     右侧：订单摘要
        当前阶段的工作内容                       当前产品项
        当前产品与字段依据                       待处理清单

底部任务栏：还需确认 1 项尺寸      [核对尺寸]
```

- “补充需求”保留对话与必要字段操作；“比较方案”使用足够宽的差异表；“核对与交接”呈现完整可审阅单据。阶段之间允许返回，订单仍由后端同一版本管理。
- 当前阶段只有一个主动作，次要动作保持可见但降低视觉权重。修改导致结果失效时，主动作切换到重新核对或计算。
- 手机优先采用“对话 / 订单”切换及固定下一步入口；键盘打开时不遮挡输入框，安全区和页面内容留出底部空间。
- 产品信息完整度保留为辅助信息；不把“100%”用作整单可生产或已发送的标志。
- 工具名称、请求号、规则置信度与运行轨迹放入可展开诊断区，用户有需要时能查到。

视觉上建议沿用现有品牌色和纸张感，正文与数字优先保证可读性；通过统一字号、间距、边框、状态色和按钮层级建立小型设计规范。红色主按钮、错误、警告不应仅靠同一种红色区分，状态同时有文字和图标。

## 4. 可拆为开发任务的工作包

### G01 · P0：统一产品定义、README 和首次进入体验

**交付**

1. 在 ROADMAP 和发布清单中采用同一完成定义及任务脚本，修正旧指标文档以 `missingFields` 清空作为最终终点的问题。
2. 同步中英文 README 的成本模型、尺寸语义、实际测试证据和严格发布门槛；把“零第三方依赖”准确限定为运行时，单列浏览器测试的开发依赖。
3. README 按“给谁解决什么 → 当前能力边界 → 启动 → 完整案例 → 交接单样例 → 能力矩阵 → 开发文档”重排。模型配置与 MCP/dsh 集成放到进阶部分。
4. 完整案例从用途出发，例如“门店开业要发给路人，约 500 张，下周要用”，展示实际追问、核对和交接结果。尺寸正文采用 mm，纸张克重采用 g/m²；A4 可作为别名与 `210 × 297 mm` 一起显示。
5. 区分“识别品类 / 补全参数 / 有条件示例计价 / 文件基础检查 / 供应商连接状态”。17 个目录品类不能被描述为 17 个均能完整估价的品类。
6. 首次进入扩展现有快捷回复，提供用途案例、自由输入和恢复历史入口；示例订单清楚标记并独立创建，不能覆盖当前订单。
7. 在 `file://` 场景明确说明需启动本地服务，并给出 README 约定的本地访问方式。启动失败区分协议错误、连接不可达、鉴权失效和服务异常。

**开发落点**：`README.md`、`README.en.md`、`docs/ROADMAP.md`、`docs/RELEASE_CHECKLIST.md`、`docs/plan/appendix-metrics.md`；`index.html`、`app.js:bootstrap`。

**验收**：两种 README 的能力与门槛一致；跟随新手路径可以完成一次本地规则模式示例；旧截图更新为本轮实际截图并注明版本/日期；不会把 390px 桌面浏览器预览称为已验证真实手机。

### G02 · P0：每个状态都有一个可操作的下一步

**交付**

1. 汇总后端已有缺失字段、待确认候选、工具阻断、文件状态和过期结果，形成当前任务卡。前端只负责展示与定位，生产校验规则继续由后端判定。
2. 清单分为“现在需要处理”和“交接时说明”。必需数量、尺寸等进入前者；没有授权供应商资料进入后者，不因此阻断合格的本地沟通单。
3. 合并同一原因产生的供应商未配置提示，显示一次“当前仅生成本地交接资料，供应商能力待核实”。
4. 每条阻断项提供定位、编辑或确认入口；明确说明为什么需要该参数。用户选“不确定”后保留待处理状态，并解释可选方案。
5. 区分“未填写 / 已填写 / 待确认 / 已确认 / 需重新核对”。模型推断不能因展示文案改变而自动获得确认。

**开发落点**：`app.js` 的流程、风险与字段渲染，`workbench.js`，必要时在 API 返回中补充稳定字段标识和阻断原因；`index.html`、`styles.css`。

**验收**：每个实际阻断原因都有可操作入口；一步点击可定位对应字段；8 名走查者至少 7 名在 10 秒内说出下一步；空订单、部分完成、待确认、可比较、可复核、确认后变更、归档均有明确状态。

### G03 · P0：统一复核、编辑和多产品作用范围

**交付**

1. 普通字段、不同尺寸语义、品类专属参数和多产品项采用一致的查看依据、编辑、清空及确认规则。必需字段被清空后恢复相应阻断。
2. 数量、单位、成品/展开/刀模/包装内外尺寸、材料、页数和颜色作为复核重点；允许先查看完整清单再作有明确范围的确认，减少无意义逐项点击。
3. 输入区、上传区、编辑表单和方案标题均显示当前产品项。文件列表展示所属产品、文件名与版本、基础检查结果；变更归属或替换文件需重新检查相关结果。
4. 产品项切换通过独立的视图/上下文操作实现，后续业务写入显式携带目标项与订单版本。优先采用稳定 `itemId`；若沿用现有 `itemIndex`，服务器必须依据当前 revision 核对映射。
5. 在途请求固定绑定发起时的产品项。切换到另一项后不能把旧响应当作新项结果展示。
6. 修改后给出影响说明，例如“数量已修改，原估算和交接确认已失效”。撤销作为一次新的受版本校验的修改，不回滚审计历史。

**开发落点**：`app.js:renderMultiProductItems/commitFieldEdit/renderDimensionRows`、文件与确认界面；`server.py`、`agent.py` 的目标项和版本校验；沿用 `fieldMeta/fieldCandidates` 和事件记录。

**验收**：2 项和 3 项订单的修改、文件、方案均不串项；待确认值在刷新后仍可找到；切换产品不新增用户聊天消息；过期响应不覆盖当前视图；已归档订单仍不可修改。

### G04 · P0：错误恢复与保存状态形成闭环

**交付**

1. 根据错误码显示字段校验失败、版本冲突、连接中断、服务异常与模型回退，不再全部归为连接失败。
2. 重要错误持续可见，提供对应恢复按钮。保留输入与编辑内容，提示正在保存、已保存或尚未确认保存成功；收到后端成功回执后才显示已保存。
3. 409 冲突先获取最新版本，展示本次修改与服务器当前值的差异；由用户决定重新应用或放弃。不能静默覆盖或无条件自动重试写操作。
4. 网络超时且提交结果未知时先读取状态/操作记录。需要可安全重试的写操作时补齐操作标识和服务器去重，再开放重试按钮。
5. memory 模式明确说明进程退出数据消失；SQLite 模式说明本地保存，保持现有完整备份入口可发现。诊断信息不展示凭据。

**开发落点**：`app.js:api/sendMessage/showToast/bootstrap`、保存状态组件；必要的 `server.py` 错误契约与写入去重。

**验收**：断开本地服务、409 冲突、无效字段、鉴权失效分别走查；输入不丢、状态可辨、恢复不需要盲目刷新；重复操作不会重复确认或创建业务结果。模型不可用时保留已有规则回退体验。

### G05 · P0 核心 / P1 排版：交接单成为可复核的正式产品产物

**交付**

1. 提供“核对与交接”页，把订单摘要、分产品规格、所选方案、文件状态和供应商待核实事项放在同一复核上下文。
2. 交接单来自后端权威版本和已校验产物。屏幕预览、Markdown/JSON 与打印视图采用同一字段映射；若版本改变，要求重新生成与确认。
3. 单据包含订单标识、产品项标识、订单版本、确认状态/时间、数量及单位、各类尺寸、材料/工艺、交期语义、文件清单和检查范围、未决事项。确认记录只代表本地人工操作，不能包装成企业身份签章。
4. 必需生产字段已经通过校验、但整单尚未确认的合格草稿可导出，并标记未确认。字段候选仍待确认时不得绕过现有交接门禁；若提供需求整理稿，只能保留缺失值与待处理候选，不能把候选当作已确定生产规格。已确认单据标记确认所对应的版本。所有形态明确供应商尚未接收；示例估算与正式报价分开标示。
5. 区分“导出交接单”和“导出完整备份”。完整消息、历史事件与审计不默认混入面向供应商的交接文件。
6. 增加 A4 打印样式，使用浏览器打印/另存 PDF；桌面工作台控件不进入打印版，多页分组、表头和长字段有明确处理。

**开发落点**：`app.js:getOrderGroups/exportOrder`、现有 handoff 与确认返回、`order_contract.py`、`styles.css`，必要时增加独立的交接单视图模块。

**验收**：单产品、2/3 产品、长工艺描述、文件待补、未配置供应商、确认后修改各有输出样例；每个关键字段与确认版本核对一致；打印无裁切和串项；独立复核者在 60 秒内找到指定产品的数量、尺寸、材料。点击导出不能自动标记为已发送。

### G06 · P1：方案比较与计价状态帮助用户作决定

**交付**

1. 把现有比较表放入足够宽的主区域。以用途和具体取舍解释方案，突出实际不同的材料、工艺、装订、印刷方式与示例交期，不重复铺满相同字段。
2. 比较必须固定同一产品、数量、尺寸和报价口径；方案故意改变的材料、工艺等清楚列出。数量单位不兼容或驱动缺失时先澄清。
3. 金额附近直接显示“示例估算”、不含税/出厂口径与未包含项摘要；来源、版本、明细和假设可展开查看。
4. `ready` 显示完整示例区间；`partial` 只显示已知费用小计与未计入项目；`blocked` 显示阻断原因及补充入口。过期结果作为历史估算单独标记，不能参与当前比较。
5. 没有可比完整价格时不标“最便宜”；推荐理由对应已知用途和明确规则，没有证据的交期不写成供应商承诺。
6. 修正方案卡内嵌交互：选择方案使用独立按钮或单选控件，展开理由不触发选中。该问题可作为前置小修复，不必等待整页重排。

**开发落点**：`app.js:renderOptions/renderOptionCompare/renderPriceEstimate`、`workbench.js:priceDetails`、`styles.css`。

**验收**：完整/部分/阻断/过期四种状态均有浏览器场景；至少 7/8 名走查者能说明两个方案的关键差异；全部走查者知道金额不是供应商报价；键盘展开理由不选中方案。

### G07 · P1：视觉规范、窄屏与可访问性随流程一起完成

**交付**

- 建立小型组件状态清单：任务卡、字段、来源详情、候选确认、方案卡、文件、错误、空状态、保存状态、交接预览。覆盖加载、无数据、失败、过期、只读，不只画正常状态。
- 统一间距、标题、数字和表格排版。正文采用易读字体，保留标题中的印刷风格；状态同时有文案和图标，避免把颜色作为唯一信息。
- 完整键盘路径、明显焦点、抽屉焦点管理与关闭后恢复；字段编辑后回到原字段，避免统一跳回聊天框。动态播报只读关键结果，避免重播整个会话。
- 验证 390/768/1280px、200% 缩放、长中文、长文件名和多项订单。高频触控目标至少 44px；正常正文对比度至少 4.5:1，必要控件与焦点边界至少 3:1。
- 按功能逐步抽取展示函数与状态派生逻辑，沿用原生 JS；拆分静态资源时同步服务端静态白名单和浏览器测试，不引入一次性框架重写前置条件。

**验收**：键盘可以完成填写、查看依据、选方案、核对和导出；窄屏主动作可达且不遮挡内容；至少补充 WebKit/Firefox 桌面走查及一台实际手机验证，结果按环境记录，不外推为全部设备支持。

### G08 · P1 / P2：让运行、定价和接入依据继续成熟

此工作包与界面闭环并行推进，以现有契约为起点。

| 方向 | 现在可做 | 完成条件 / 外部依赖 |
| --- | --- | --- |
| 默认存储策略 | 在 OrderStore 之外定义可配置的备份、归档与保留策略边界，默认保留追溯记录。使用 SQLite 一致性备份机制，输出版本清单，提供恢复校验流程；界面只展示模式、保存结果和备份入口。 | 用隔离数据库演练备份、恢复、消息/审计完整性；与现有 CAS 和迁移兼容。容量策略不得默认删除应保留记录。企业数据库等待实际部署需求。 |
| 成本依据可解释 | 为现有公式提供一份人工可复核算例和模型假设清单，说明面积、损耗、开机、最低收费等怎么算；公开各品类可计价条件。保留当前 CSV 校准草稿与活动版本隔离。 | 算例与引擎金额一致，未知参数明确阻断/部分计价；材料单价没有依据时仍标示例。取得可用授权报价后才做真实校准及复核发布。 |
| 更接近生产的成本模型 | 对首批品类评审大纸规格、拼版利用率、设备与损耗等模型差距，先列输入要求和规则，获得依据后扩展成本驱动。 | 依据与样例齐备后再实施；不能用更多参数包装未经校准的估算精度。 |
| 通用供应商接入包 | 在已有协议/registry/mock 上整理最小连接器示例、字段映射、能力与有效期说明、错误/未知状态处理和契约测试运行方法。 | 第三方开发者可在不修改核心订单逻辑的情况下注册本地 mock 并通过契约测试；盛大保持未配置/仅导出，真实 transport 等待授权与官方协议。 |
| 运行可靠性 | 按现有 ROADMAP 核对整请求截止时间、模型状态按会话隔离、超时/回退反馈等未闭合项，纳入对应运行时验收。 | 用明确故障场景验证，保留实际环境结果；界面优化不能替代这些发布门槛。 |

## 5. 最小度量与验收材料

第一轮先用统一走查表获取真实卡点，不必先建设分析后台。若加入本地事件，最少区分 `task_started`、`review_ready`、`confirmation_recorded`、`confirmation_invalidated`、`export_requested`、`artifact_generated`、`task_abandoned` 和 `operation_failed`。

事件仅保留必要的随机标识、版本、品类枚举、时间和结果代码，不记客户原话、联系方式、文件内容或密钥，不自动发往远端。匿名化标识不能简单截短订单号。刷新或重试不得重复计入同一次完成；确认失效后不能沿用旧完成状态。度量记录与业务审计区分：度量失败不阻断整理订单，必要审计失败仍按现有业务规则处理。

每个工作包交付五类材料：

1. 当前问题与目标状态图；包含至少一个错误或边界状态。
2. 可运行的界面或接口变更，注明依赖和回退方式。
3. 针对改变行为的必要回归证据，沿用现有 Python/API/浏览器基础。
4. 当前版本截图或实际输出样例；演示与合成数据有明确标记。
5. 简短验收记录：通过项、未测环境、发现的问题、是否满足进入下一步的条件。

核心任务脚本建议包括：用途模糊的单品需求；成品与展开尺寸同时出现；修改数量使结果失效；两个产品分别绑定文件；无模型规则回退；本地服务中断恢复；双窗口修改冲突；归档查看与导出。用合成脚本验证功能，用首次用户走查验证可理解性，两类证据分别报告。

## 6. 推进顺序与职责

按交付依赖推进，不按天数承诺：

| 阶段 | 做到什么 | 进入下一阶段的证据 |
| --- | --- | --- |
| A：统一目标与基线 | G01 的完成定义、文档事实修正、能力矩阵；记录旧流程走查基线 | 同一个任务在 README、界面与验收表中有相同终点；关键问题清单明确。 |
| B：打通一单 | G02、G03、G04，加上 G05 的版本一致性、复核和交接核心；提前修复方案键盘误操作 | 标准单品从输入到打开导出文件完整走通；修改、错误和恢复没有破坏确认或产品归属。 |
| C：改善决策与呈现 | G05 打印版、G06、G07；完善多产品和窄屏体验 | 完成 8 人走查、输出审阅和所声明浏览器范围验证；用实际失败原因安排下一轮。 |
| D：增强依据与扩展 | G08 按数据和部署条件逐项成熟 | 存储恢复演练通过；价格来源与模型适用范围明确；接入者能完成本地协议验证。真实连接单独等待授权。 |

设计负责人负责用户流程、信息优先级、状态文案和走查；前端负责可交互组件、焦点、窄屏与展示一致性；后端负责权威状态、版本/确认约束、错误恢复和存储；印刷业务复核者负责参数与计价口径；质量负责人组织回归、用户走查和输出检查。可以由同一开发者承担多种职责，验收责任仍需清楚。

近期最适合直接开工的六张任务卡：

- **T01**：修正中英文 README 与发布指标，给出一条从用途到交接单的可复现路径。
- **T02**：统一下一步与阻断清单，合并重复供应商提示。
- **T03**：统一字段复核组件、当前产品作用域和切换行为。
- **T04**：实现持久错误卡、保存状态与 409 冲突恢复。
- **T05**：核对交接输出与确认版本一致，明确草稿、文件待交付和未发送状态。
- **T06**：修复方案键盘误选并开展第一轮用户走查，再根据卡点安排主区域比较和打印排版。

本计划不以新增主 Agent / 子 Agent 产品结构为目标。当前供应商中立接口、可替换存储、mm 规范和真实语料发布门槛作为后续开发的既有约束继续保留。
