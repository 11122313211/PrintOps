## 一、项目背景与当前定位

PrintOps 是一个面向市场、设计和采购团队的本地印刷订单 Agent。用户只需描述"要印什么、
用于什么场景"，系统就会逐步补齐印刷品类所需参数，解释工艺取舍，生成可询价、可交接的
订单草稿。北极星目标是：让非印刷专业用户在 10 分钟内把模糊需求整理成完整、可靠、
可追溯的印刷订单。

产品分工原则自 v0.8.0 起保持稳定，所有后续演进都必须在这条边界内进行：

- **模型**负责理解、追问、解释和选择工具；
- **确定性规则**负责字段规范化、品类参数、工艺约束和风险判断；
- **工具**负责预检、方案、询价准备和导出等动作；
- **人**负责确认高风险结果（生成交接单与未来的外部提交必须经过人工确认）。

当前 `1.0.0` 代码基线已完成 1.0 发布门槛七项中的五项代码门槛（静态白名单与本地令牌、
socket 级 HTTP 测试、Key 风险提示与敏感扫描扩充、补丁引擎合并与死代码清理、SQLite WAL
与损坏会话自愈），并额外落地了 LLM 接口 SSRF 校验、真实脱敏评测机制（加载器、四态判定、
≥20 例硬门槛、标注辅助工具）与真人走查脚本。剩余两项人工事项（真实脱敏语料 ≥20 例、
一轮真人走查）完成后，才可按通用定义把候选基线转为稳定 1.0 发布。

### 2.4 已确立的工程约束（所有路径必须遵守）

1. **零第三方依赖**：运行时只用 Python 标准库 + 浏览器原生能力。任何路径不得引入 pip 包或前端框架；开发期工具（测试运行器、linter）允许存在于 dev 依赖，但不得进入运行链路。
2. **确定性边界**：模型输出永远经过受限补丁白名单与工具白名单；订单校验、能力匹配、幂等与人工确认必须留在本地确定性代码。
3. **本地边界**：默认只绑 `127.0.0.1:4174`；静态白名单 + 进程内令牌 + 同源校验是安全基线，任何新接口不得绕过 `_guard()`。
4. **版本可追溯**：知识版本（knowledge version）、价格模型版本（pricingModelVersion）、状态 schema 版本（STATE_SCHEMA_VERSION）三套版本号各自独立演进，响应必须携带。
5. **跨平台一致**：macOS/Linux/Windows 共用同一套逻辑；启动脚本可分叉，逻辑不分叉。Windows 语义（路径、连接关闭 RST 行为、文件权限）必须在测试中覆盖。
6. **文档纪律**：每个版本必须同步 CHANGELOG、README、ROADMAP；行为变化必须有对应测试。

## 五、横切关注点

### 5.1 测试策略

- **金字塔**：底层（order_model/nlu/tools）单测为主；边界（server 契约 + socket 级 HTTP）双轨；端到端（Playwright 冒烟）只覆盖四条关键路径——首次对话、多产品拆分、错误恢复、刷新恢复。
- **评测即门禁**：字段准确率与完整率是发布门禁，不是参考指标。真实语料不足 20 例时允许软门槛，但禁止长期停留在"待补充"状态（连续两个版本不补充则视为发布阻碍）。
- **Windows 语义**：连接排空（413 drain）、RST 对 backlog 的影响（v0.11.0 已修）、文件权限、路径大小写——每个涉及 I/O 的路径都要在 Windows CI 上验证。
- **性能预算**：合成评测平均响应 <50ms；`render()` 单帧面板更新数 ≤3；首字反馈 <1s（LLM 模式）；启动到可交互 <2s。

### 5.2 风险登记册

全局与各路径的完整风险登记册（含触发信号与监控点）见附录 A；执行期每两周评审一次，触发信号出现的风险升级为"活跃"。以下为最高优先级速览：

| 风险 | 影响 | 缓解 | 所属路径 |
| --- | --- | --- | --- |
| 真实语料迟迟不到，1.0 无限延期 | 发布停滞 | 语料征集纳入每周例会；不足 20 例时只能保持候选/内部预览，不得用走查结论替代真实语料硬门槛 | 路径 5 |
| 流式解析对非标准厂商 SSE 兼容性差 | 聊天不可用 | 白名单式 delta 解析 + 同步回退链 + fake SSE 测试服务器 | 路径 1 |
| 前端拆分引入回归 | 功能回退 | 面板级渐进迁移 + 每步全量回归 + 迁移期禁止功能改动 | 路径 2 |
| 供应商平台行为不可控 | 外部依赖 | 沙箱先行、只读三类接口、五件套强制、契约测试 | 路径 3 |
| 零依赖约束限制选型 | 实现成本上升 | 优先标准库与浏览器原生能力；确需依赖时先在计划书评审 | 全局 |

### 5.3 治理约定

- **版本号**：语义化版本。0.x 阶段 minor 版本承载功能，patch 只承载修复；进入 1.x 后 minor 为兼容功能、major 为破坏性变更。
- **分支与提交**：main 单分支；提交按 CHANGELOG 分组（feat/fix/refactor/test/docs/chore）；每个功能提交必须包含测试。
- **评审清单**（每个 PR/提交组）：确定性边界是否被绕过？安全基线（白名单/令牌/SSRF）是否被绕过？版本号（知识/价格/schema）是否需要递增？CHANGELOG 是否同步？Windows CI 是否通过？

## 六、本计划书的使用方式

1. 排期会议以本总纲第四节里程碑为骨架，按路径文档的"分阶段实施步骤"拆任务卡；
2. 每完成一个阶段，在对应路径文档末尾追加"实施记录"（日期、实际工时、偏差原因）；
3. 任何路径的范围变更必须回写本总纲第三节总览表，保持单一事实源；
4. 路径间冲突（如同时动 `app.js`）在排期时串行，避免合并冲突与行为漂移。

### 执行节奏约定

1. **单版本聚焦**：同时推进的路径 ≤3（含一条主线）；动 `app.js` 的任务卡彼此串行；
2. **每卡即 PR**：一张任务卡 = 一次提交组（代码 + 测试 + CHANGELOG 行），验收标准即评审清单；
3. **周三评测日**：每周三跑一次 `--record`，趋势恶化（真实语料准确率周环比下降 >2 个百分点）即升级为活跃风险；
4. **两周风险评审**：按附录 A 逐条过活跃风险，触发信号出现即指定负责人与应对时限；
5. **发布冻结窗**：版本 DoD 检查开始后只允许修缺陷，不接受新卡。
